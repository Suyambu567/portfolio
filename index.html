01

Tamil/Tanglish Citizen Complaint Voice Assistant

 Open fileClose file

Technical evidence

Results (measured)

Fine-tuning the ASR on the deployment's own code-mixed speech is what moved the system, after swapping pretrained models did not. Two rounds of fine-tuning, each evaluated against the version it replaced:

Speech recognition — measured on held-out clips from this project
ComparisonWERCER English words kept in Latin script
Untrained base model → first fine-tune (89 clips) 80.1% → 55.0% 77.2% → 39.4% 0% → 37.4%
First fine-tune → second fine-tune (107 clips) 49.8% → 46.6% 32.8% → 30.8% 37.9% → 38.5%
Spontaneous citizen clips only (9 clips) 83.8% → 69.3% — —

Runtime, measured on the same evaluation: average 0.533 s, p50 0.474 s, p95 1.091 s, real-time factor 0.139.

Read the WER honestly. 46.6% is high in absolute terms. Code-mixed Tanglish is punishing to score — a word written in the other script counts as a whole error — so the meaningful figure is the gap between two systems on the same clips under the same metric, not the absolute value. District and area name recall remains unsolved at 0 / 6 across both rounds.
Engineering details
Problem

Filing a civic complaint means a form: the right department, the right category, an address written the way the system expects. A citizen who would say "enga area-la water problem irukku" out loud has to translate that into someone else's schema before anything happens. The speech-first route removes the form, but only if the system can handle how people actually talk — Tamil and English mixed inside a single sentence.

Solution

A spoken-dialogue system that takes a complaint from speech to a routed, ticketed record without a form. Audio streams from a mobile client to a Python voice server over a WebSocket; voice activity detection decides when the citizen has finished speaking; the utterance is transcribed, classified into one of 24 civic issue categories, and checked for the details a complaint needs. When the area or street is missing, the assistant asks for it and waits, rather than filing an incomplete record. The finished complaint is mapped to one of 25 departments, stored with a sequential ticket number, and read back in spoken Tamil.

Technology
  • Client: Flutter mobile app
  • Transport: WebSocket audio streaming
  • Server: Python, asynchronous
  • VAD: WebRTC VAD, 20 ms frames
  • ASR: Whisper-medium fine-tuned with LoRA, served through CTranslate2; cloud ASR providers as alternate routes
  • Understanding: LLM provider plus a rule-based intent and location layer
  • TTS: neural text-to-speech for the Tamil reply
  • Testing: pytest; an offline harness drives the dialogue with text and asserts what was filed
Engineering challenges
  • Code-mixing broke every off-the-shelf ASR. Each engine tested transliterated the English words into Tamil script, which corrupted the routing stage downstream. The base Tamil Whisper model kept 0 / 289 English words in Latin script.
  • Turn-taking. Deciding when a speaker has stopped — rather than paused — is what makes a voice assistant feel usable, and it is handled at the VAD frame level.
  • Incomplete complaints. Spontaneous speech rarely contains everything a complaint needs, so the dialogue has to distinguish a problem description from an area name and ask only for what is missing.
  • Correctness that a crash test cannot catch. The failures that matter are wrong filed data — a problem fragment parsed as an area, an unroutable department — so the test harness asserts the resulting record, not that the code ran.
My contribution

Implementation verified in the project repository:

  • Real-time voice server: WebSocket audio ingestion, VAD-driven turn-taking, audio preprocessing ahead of transcription
  • Complaint dialogue: intent and category classification over 24 civic issue types, including a Tanglish keyword layer
  • Location understanding: area, street, sub-area and ward extraction with alias and fuzzy matching, plus the follow-up questioning that fills the gaps
  • Department routing across 25 departments, ticket numbering that survives restarts, and a query CLI over the filed complaints
  • ASR fine-tuning: dataset preparation from human-verified transcripts, LoRA training, evaluation harness, and the promotion gate on WER, CER and latency
  • Test suite covering turn-taking, transcription confidence gating, TTS caching and the dialogue itself

This system was built in a private repository. No source code, internal URLs, infrastructure details or citizen data appear on this site — only architecture, methods and evaluation results.

02

Tamil BPE Tokenizer — built from scratch

 Open fileClose file

Technical evidence

What the model learned

Trained for 50 merges, the first rules the algorithm found are exactly the units Tamil orthography is built from — a consonant joined to its pulli, and a consonant joined to its vowel sign:

merge 1  →  ('ன', '்')  →  ன்
merge 2  →  ('ர', 'ு')  →  ரு
merge 5  →  ('க', '்')  →  க்
merge 6  →  ('க்', 'க')  →  க்க

Nothing in the code knows anything about Tamil grammar — the merges are driven purely by frequency, and they converge on the writing system's own building blocks.

Example input and output

Produced by loading the trained merge rules and encoding:

"நான் பள்ளிக்கு" → ['நான்', 'பள்ளிக்கு'] — 2 tokens
"நான் இன்று பள்ளிக்கு சென்றேன்" → ['நான்', 'இன்று', 'பள்ளிக்கு', 'சென்றேன்'] — 4 tokens
"தமிழ் ஒரு அழகான மொழி" → ['தமிழ்', 'ஒரு', 'அழகான', 'மொழ', 'ி'] — 5 tokens

The third line is the interesting one. Words the tokenizer saw during training collapse into single tokens, while மொழி — which it did not finish learning — splits into மொழ + ி. That is BPE overfitting a small corpus, visible in one line of output: with enough merges relative to the data, the model memorises whole words instead of learning reusable subwords, and only unseen text reveals it.

Engineering details
Problem

Tokenization decides what every downstream NLP model can see. Tamil makes that harder than English: it is agglutinative, so one word carries case and postpositions that English spreads over several words, and its script composes characters from a consonant and a dependent vowel sign. Split at the wrong boundary and the pieces are not linguistic units at all. Word-level tokenization explodes the vocabulary; naive character-level tokenization throws away structure.

Approach

Byte Pair Encoding, written from first principles rather than called from a library, so the merge behaviour is inspectable at every step: build the character-level vocabulary, count adjacent symbol pairs, merge the most frequent pair, repeat. The trained merge rules are persisted as JSON and reloaded for encoding, and a separate vocabulary component maps tokens to integer IDs and back.

My contribution

Implementation verified in the repository:

  • The BPE trainer end to end — vocabulary construction, pair statistics, best-pair selection, merge application, and the training loop
  • Encoder that replays learned merges over unseen text, and the decoder
  • Model persistence: merge rules saved to and loaded from JSON with Unicode preserved
  • Tamil Unicode validator over the U+0B80–U+0BFF block, and a character-level tokenizer for comparison
  • Vocabulary component with token↔ID mapping and its own save/load
  • YAML-driven configuration and corpus loading, so a training run is reproducible from config
Scope and limits

This is a fundamentals project, not a production tokenizer. It was trained on a small demonstration corpus for 50 merges. It carries no benchmark against SentencePiece or any other tokenizer, and no evaluation metrics — because none were measured, and inventing them would defeat the point of the exercise. What it demonstrates is the algorithm implemented correctly from scratch and applied to Tamil script.

A second, smaller Random Forest was exported to JSON and re-implemented in JavaScript so the same classification runs entirely in the browser with no backend and no network calls: accuracy 0.9342 against a 0.6312 baseline, cross-validated at 0.9367 ± 0.0028, in a 256 KB model file.

Both models are evaluated on synthetic data. The dataset is produced by a generator that encodes how fake engagement behaves — mass following, bot likes without comments, young accounts, promotional bios — but it is not a sample of real accounts. The 94.09% figure measures the pipeline, not real-world performance on live profiles, and the application itself states this to the user. A control run of the same pipeline on randomly-labelled data scores 0.5110 against a 0.5045 baseline, which is what confirms the headline number reflects signal rather than leakage.
Engineering details
Problem

Fake profiles spread misinformation, run fraud and inflate social influence. Detecting them from account metadata alone is a classification problem over mixed feature types — and the classes are imbalanced, because fake accounts are the rarer class. That makes accuracy on its own useless as a measure of success: a model that guesses the majority class every time already scores well above 50%.

Approach

A full pipeline: cleaning and de-duplication, feature engineering across three feature families, encoding and scaling inside a fitted pipeline, class-imbalance handling applied only after the train/test split, then gradient-boosted trees. Every accuracy figure is reported next to the majority-class baseline, and the difference between them — the lift — is treated as the real result.

Features and NLP
  • Profile: has a profile picture, full-name word count and length, digit-to-length ratio in the name, bio length, presence of an external URL
  • Behavioural: post count, follower count, follow count — the follow ratio and whether engagement matches audience size
  • Textual (NLP): the bio, vectorised with TF-IDF inside the same fitted pipeline as the numeric features
  • Encoding: a ColumnTransformer combining standard scaling, TF-IDF over the bio, and one-hot encoding for categorical fields

Training and serving call one shared feature-building function, so a feature cannot be computed one way at fit time and another way at request time — and a test asserts the two feature frames are identical, column for column. Where an optional field is omitted from a request, the value is imputed and the response reports which fields were imputed.

My contribution

Implementation verified in the repository:

  • Preprocessing: missing-value imputation, duplicate removal, label validation
  • Feature engineering across profile, behavioural and textual attributes, shared between training and serving
  • XGBoost training with class-imbalance strategy selection, plus the evaluation module — confusion matrix, cross-validation, baseline comparison
  • An algorithm benchmark comparing candidate models on the features the API actually serves
  • FastAPI service with Pydantic request validation, a model-info endpoint that reports metrics and training-time warnings, and version checking on load
  • Browser model: Random Forest exported to JSON and evaluated in vanilla JavaScript with the same scaler statistics and TF-IDF vocabulary, plus per-feature contribution explanations
  • GitHub Actions workflow that validates and publishes the browser app
