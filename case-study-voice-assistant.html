Tamil/Tanglish Citizen Complaint Voice Assistant

An end-to-end Voice AI system: spoken Tamil or Tanglish in, a routed and ticketed civic complaint out, and a spoken Tamil reply back — with no form to fill in at any point.

Scope of this page. This system was built in a private repository. Nothing here contains source code, internal URLs, infrastructure details, credentials or citizen data — only architecture, engineering decisions and measured evaluation results.

01 — Problem

The form is the barrier

Filing a civic complaint normally means completing a form: choosing the right department, picking the right category, and writing an address the way the system expects it. That asks the citizen to do the classification work before anything happens — and the people most affected by a broken streetlight or a water outage are often the least able to do it.

Speech removes the form, but only if the system can handle how people actually speak. In Tamil Nadu that means code-mixed Tamil and English inside a single sentence: "enga area-la water problem irukku", "government scheme pathi". It also means spontaneous speech, which is rarely complete — someone will describe the problem vividly and never mention which street they are on.

So the system has to do three things a form does for free: understand code-mixed speech, work out what is missing, and ask for it.

02 — Solution

A spoken dialogue that ends in a filed complaint

A mobile client streams live microphone audio to a Python voice server over a WebSocket. Voice activity detection decides when the speaker has actually stopped rather than merely paused. The captured utterance is preprocessed and transcribed, then classified into one of 24 civic issue categories while a location layer extracts the area, street, sub-area or ward.

If the complaint is missing something it needs, the assistant asks for that one thing and waits, rather than filing an incomplete record. Once complete, the complaint is mapped to one of 25 departments, stored with a sequential ticket number that survives server restarts, and read back to the citizen in spoken Tamil.

It is not a chatbot with a voice attached. Every stage — turn-taking, transcription, classification, slot filling, routing, ticketing, speech synthesis — is part of one real-time loop, and each one can fail in a way that produces a wrong filed record rather than an error message.

03 — Architecture

How a spoken sentence becomes a routed ticket

The parts that are not obvious

  • Turn-taking lives at the frame level. Voice activity detection runs over 20 ms frames, which is what makes the difference between an assistant that interrupts and one that lets a person finish a sentence.
  • Classification is a layer, not a prompt. Category detection scores an utterance against each issue type using a keyword layer built for Tanglish, before and alongside the LLM — so an ambiguous transcript degrades into an unclassified complaint rather than a confidently wrong department.
  • Location is its own problem. Distinguishing an area name from a description of the problem is genuinely hard in spontaneous speech, and it is handled by a dedicated extraction layer with aliases and fuzzy matching rather than being left to the model.
  • The follow-up loop is the reason it works. When a required detail is absent, the assistant asks for that one thing and returns to listening. Without it, most real complaints would be filed unroutable.
04 — My contribution

What was implemented

Verified against the project repository:

  • Real-time voice server — WebSocket audio ingestion, VAD-driven turn-taking, audio preprocessing ahead of transcription, and session handling for concurrent callers.
  • Complaint dialogue — the dialogue state machine, intent and category classification across 24 civic issue types, the Tanglish keyword layer, confirmation and cancellation handling.
  • Location understanding — area, street, sub-area and ward extraction, alias normalisation, fuzzy matching, and the checks that separate a place name from a problem description.
  • Routing and records — the department mapping across 25 departments, sequential ticket numbering that resumes after a restart, and a command-line tool to query filed complaints by ticket or by department.
  • ASR fine-tuning — dataset preparation from human-verified transcripts, LoRA training on a Tamil Whisper base, the evaluation harness, and the promotion gate that a new model must pass on word error rate, character error rate and latency before it replaces the live one.
  • Speech output — Tamil response generation, text-to-speech routing and response caching.
  • Testing — a pytest suite covering turn-taking, transcription confidence gating, TTS caching and the dialogue, plus an offline harness that drives the whole conversation with text and asserts the resulting record.

Measured, not claimed

What these numbers do and do not say. A 46.6% word error rate is high in absolute terms. Code-mixed Tanglish is punishing to score, because a word written in the other script counts as a whole error even when a human would read it correctly. The meaningful comparison is between two systems on the same clips under the same metric — not the absolute value, and not a comparison against English WER figures.

Two weaknesses stayed unsolved across both rounds: district and area name recall (0 / 6), and Tamil-only word accuracy, which barely moved despite a training batch aimed directly at it.

07 — Lessons

What the project actually taught

  • Domain data beat model shopping. A year's worth of swapping pretrained models produced 0% English survival. Roughly an hour of the deployment's own labelled speech produced 38.5%. The lesson is where to spend effort, not which model is best.
  • The headline average hid the real gain. Round 2 barely moved the read-aloud clips (46.7% → 44.5%) but improved spontaneous citizen speech by 17% relative — and spontaneous speech is the only kind production receives. Reporting only the aggregate would have understated the improvement and pointed the next round of work in the wrong direction.
  • Read-aloud training data plateaued. Going from 10 to 60 minutes bought around 25 WER points; 60 to 73 minutes bought 3.2. More prompts were no longer the answer — labelling genuine recordings was.
  • Improvement is a trade-off, not a win. The second round shifted the script prior toward Tamil, causing regressions where the reference keeps English in Latin script. Overall English survival still rose, so it shipped — but it was a trade to watch, not a free gain.
  • Test what gets filed, not that the code ran. In a voice pipeline the dangerous failures are silent: a problem fragment parsed as an area name, an unroutable department. Import-level tests prove nothing. The offline harness drives the whole dialogue with text and asserts the record that comes out.
  • Promotion needs a gate. A new model replaces the live one only after clearing thresholds on word error rate, character error rate and p95 latency together — otherwise a quality gain quietly becomes a latency regression.
